# Desk

The **desk** is the one place where everything that waits on Tobias lands: staged lines in agent chats, drafted customer replies, PRs stuck at changes-requested on orbit or orbot, agent runs that only need a "go". It is also the one place that keeps the two executors fed: a pre-flight dispatches `/plain-agent-loop` and `/hermes-harvest` in the background whenever they are due, so the desk never runs them itself. The desk is **live** (Tobias, 2026-10-09: no sittings, no clock): the desk pane stays open in a session, reruns `desk.py` by itself every 10 minutes and after every close, and Tobias starts a **card** whenever one is worth it (`w` on the pane, `/desk`, or by saying so). Nothing opens and nothing closes; the count that matters is "closed today". Each card is a **brief**: one physical act with its consequence already drafted, and it ends in exactly one **verb**. The agent **pushes right**, doing every bit of preparation before the checkpoint so Tobias is asked once, late, with everything ready, and then executes; Tobias only chooses.

Sources and per-lane recipes live in [CARDS.md](CARDS.md). State lives in `~/orbit-scratch/desk/desk.json` (deferrals, seen counts, the done log) and survives every restart. Local tasks live in `~/orbit-scratch/desk/tasks.json`: when Tobias says "put X on my desk" and X has no thread, PR or ticket, add it with `task.py add` (lane TASK, recipe in CARDS.md). The loop's `state.json` is read, and its `status` captions are written back when a card closes, so the pipeline board and the next `/plain-agent-loop` tick see what happened here.

## Step 0 — pre-flight (agent, silent, under 30 s)

On `/desk`, run `python3 ~/orbit-scratch/desk/desk.py` once; its second line is `PRE-FLIGHT: due → …`. When a card starts from the pane instead, the desk block beside the prompt carries the same line (`Pre-flight due: …`); dispatch each executor once per conversation. For every executor listed as due, start one background Agent (subagent_type `general-purpose`, prompt from the Pre-flight table in [CARDS.md](CARDS.md)) and print one line: `Dispatched: loop tick (respawn T-107), harvest (3 open entries).` Never wait for them; their results are cards on a later run. When nothing is due, print nothing. The weekly `/sentry-sweep` starts from the Superset cron `weekly-sentry-sweep` only; the desk never starts one. Since 2026-09-11 the desk owns the sweep's follow-through: its paused fix pass and its open decisions are SWEEP cards (recipe in CARDS.md).

## Step 1 — gather and rank (agent, silent)

Print the header and TOP SIX from the same `desk.py` output verbatim (links included, one line per card, the `→` act under it). The ranking is the script's: work from the top, defer a card but never reorder by hand. It moves between cards (a new thread of today lands above everything); the card being worked keeps its place on the pane until it has its verb. Lanes come from the regex detectors in `desk.py`; since 2026-09-23 TypeSafe Jev (`~/orbit-scratch/agent-loop/jev/desk_lanes.py`) lifts a row the regex left unmatched into SEND/REVIEW/REPLY/RUN when it is ≥ 0.85 confident. A caption that waits on a teammate's decision is no card: questions to teammates go out on one channel, OrBot's Ask-Orbit on Slack (TODO: route via Ask-Orbit, see orbot adapter orbitInputRequest). `JEV_DESK=0 python3 desk.py` turns it off for a run. Done when the six are on screen with their minutes.

One or more refs as arguments (`/desk T-120`, `/desk T-120 ORB-203 T-114`) **pin** them: run `desk.py <refs…>` in Step 0 instead of the bare call. Every pinned ref becomes a FAST card above the ranking (score 1000+, argument order kept) and stays at the top on every later run until it gets a verb, which unpins it. The FAST recipe in [CARDS.md](CARDS.md) is the fast track: read the thread or ticket live, claim it, validate, draft the reply, or hand it to a worker, in this session. Refs and a tenant id or `next` can be combined.

`wins` argument: print `desk.py --wins` and stop. `next` argument: skip to Step 3 for the top card of the desk as it stands (no `desk.py` run when the desk block is beside the prompt). A tenant id as argument (`/desk acme`) scopes the desk to that tenant: run `desk.py --tenant <id>`; the pane's own runs keep that scope (cards.json records it, the pane header shows it) until a bare `desk.py` widens it again. A thread belongs to the tenant when its `tenant_id` field says so (Hermes and Sentry auto-flags) or when the customer's company or email domain contains the tenant id (`dana@acme.example` → acme, `north-wind.example` → northwind; `~/orbit-scratch/desk/tenants.json` maps the exceptions). The tenant desk is the whole desk for that customer: besides the scoped loop, gap and PR cards, every TODO thread of the tenant that no agent, HORST or release owns (no loop entry) is one FAST card, `tenant:<ref>`, worked with the FAST recipe. A tenant run never rewrites `board-sync.json` or `release-watch.json`; the unscoped run owns the board.

The day's threads always come first (Tobias, 2026-10-09): every unscoped run reads the Plain threads opened today or with a customer message today (Europe/Berlin), gives each one without a card a FAST card `today:<ref>`, and ranks threads opened today above everything (1800+), threads with a customer message today right under them (1700+), both above pins; only desk.json `top` stays higher. The header lists them as `today: T-130, …`. The `today` argument (`/desk today`) still exists for a desk that shows nothing else: run `desk.py --today` (`--since YYYY-MM-DD` for another day), and the pane keeps that scope like a tenant's; cards from older threads stay off the desk, and like a tenant run, a today run never rewrites the board files.

## Step 2 — start the top card (one line)

Say where the desk stands once: `Desk: N waiting, K closed today.` If REVIEW cards number five or more, add the finishing-move line: `N of your PRs sit at changes-requested; nothing new is worth starting until three close.` Then work the top card (Step 3). A card started from the pane (`Work desk card <id> now`) or by name skips Steps 1 and 2.

## Step 3 — work one card

For the one card that was started, in this order:

0. **Start from the prepared brief when one exists** (2026-10-13). After every gather, `desk-prepare.py` drafts the top five single cards in the background (scripts collect the thread, the memory block, the PR and the local file; one headless sonnet run per card writes `~/orbit-scratch/desk/briefs/<id>.json`: `fact`, `draft`, `options` recommended first, `checks` with their evidence, `openChecks`, `resolved`). The pane marks such a card `◆` and shows its PREPARED block; the desk block beside the prompt names the file. Read it, verify each `openChecks` line live, confirm no customer-visible message is newer than `preparedAt`, then go to step 2 with the brief's fact, draft and options (edited where a check changed them). A brief with `replyReady` already carries the drafted set (`Send it` first); a customer-text brief whose open checks all pass live gets that set too. Before the card goes up with it, write the draft to `~/orbit-scratch/desk/drafts/<ref>.txt` and `pbcopy` it. Skip the raw reads the brief already did; its `.ctx.md` holds what it saw. A brief is bound to the caption it was written for; a changed caption drops it and the next pass writes a new one. No brief, or a brief whose checks fail: step 1 as before.
1. **Push right** (agent, silent, appetite 2 min): fetch what the verb needs per the lane recipe in CARDS.md — the staged line, the draft, the PR state, the human gates — and draft the default consequence. A card that ends in customer text (REPLY, NOTIFY, PROMISE, FAST) carries a `memory:` line from `desk.py` (tenant, requester, du/Sie, greeting, role, matching known issues); before drafting, read the whole block with `python3 ~/orbit-scratch/desk/memory.py show <ref>` and draft from it: address form, greeting and sign-off habits, register, the requester's role, the tenant's rollout state, and any known issue whose mechanism you verified on this thread. The draft checks name the memory files read (or "no memory: company unmapped"). The customer text never quotes memory, tenant ids, sources or inferred facts (orbot policy.md rule 6). Reply drafts go to the clipboard with `pbcopy`. A draft goes to the clipboard only after every claim in it was checked against live data or code (memory `validate-customer-drafts`); otherwise the card carries the open checks, not a draft. When preparation shows the card is already resolved (reply sent, PR merged, line already submitted), close it with `do` and say so in one line.
2. **Present** with the `desk_card` tool (the desk mod registers it): `card_id`, `fact` = the single fact that decides it, `draft` = the drafted consequence, `options` = that lane's fixed set from CARDS.md, recommended first, each with its verb. The pane shows them as hotkeys; end the turn after the call. Tobias's pick arrives as the next message, `Re desk card <id>: <option>`, and that turn executes it. A customer-text card with a checked draft shows `Send it · Edit then send · I sent it already · Defer · Drop`, `Send it` first (CARDS.md, Lanes). The send confirmation is that lane option, never an extra question: the pick `Send it` is the approval, and the next turn sends. `AskUserQuestion` only for a question that is no lane option: the text of an `Edit then send`, one answer per member of a SEND or STALE batch, a worker's D<n> decisions, the MEMORY harvest.
3. **Execute** the chosen verb per the recipe. Outward actions (a customer reply, a Slack message to a person, a merge, a production write) run only on the explicit option that names them; everything else the agent does at once. A customer reply goes out as Luna through the orbot adapter (`luna-send.py`, recipe "Sending as Luna" in CARDS.md), not through `reply_to_thread` under Tobias's user: the customer's answer then lands in the adapter's `luna_followup` job and the customer sees one machine user. `reply_to_thread` is the fallback only when the adapter refuses (exit 3) and Tobias says so.
4. **Harvest** (agent, one question, only when there is something): after the verb on a customer-text card, list what this card taught about the tenant or the requester that the memory block did not have — a role, an address form or greeting habit, who owns a config, a rollout state, a recurring theme — one line each with its source (thread, note, code path) and a confidence. Put them in one `AskUserQuestion` (header MEMORY, multiSelect, each line an option, "store" by picking). Every picked line: `python3 ~/orbit-scratch/desk/memory.py propose --ref <ref> --tenant <id> [--person c_… --name "…" --role "…"] --section observed|approved|inferred --confidence … --source "…" "<fact>"` (a new requester needs `--role`). Nothing learned: skip the question, say nothing. The queue becomes the `memory:pr` card (CARDS.md).
5. **Record** with the `desk_close` tool: `card_id`, `verb`, `note`, and for a loop or gap card the new `caption` (under 50 chars) in the same call, so the board tells the truth and the closure binds to it. A `defer` passes `trigger` and `act`; "later" is never a trigger. The tool runs `desk-close.py`; the mod denies that script over Bash for a verb (`caption` alone still runs). The tool's answer is the restate line. The desk never publishes the board page; the next loop tick does.
6. **Restate** the tool's answer in one line: `Card <id> closed (<verb>). Closed today: K.` and name the card now on top. Then stop: Tobias starts the next card (`w` on the pane, `/desk next`, or by saying so). The pane ranks again on its own in the meantime.

Done when the card has one verb in the log and its caption is current.

## Wins

`/desk wins` prints the day's log as links (closed / deferred / dropped, one line each) at any time. There is no closing step.

## Rules

- **Touch once.** Every card ends in one verb: `do` (agent finishes it now), `decide` (one closed question, then the agent acts), `delegate` (agent drafts, Tobias says send), `defer` (trigger + act), `drop` (reason).
- **A brief, not a draft.** The card arrives with the consequence drafted and the deciding fact on top; Tobias confirms or edits, never composes from scratch and never reads raw material.
- **One card at a time.** A card is worked from its start to its verb; the next one starts when Tobias says so, never by itself.
- **Appetite over willpower.** A card that overruns its minutes goes back to the desk with `defer` and a re-bet note.
- **Expiry.** A card seen on three days without a verb is marked EXPIRING and its options collapse to `defer` / `drop`.
- **A shipped fix waits for its release, not for a person.** Deferring a customer note until a deploy always uses `deployed:<env>:<pr>` (or `appstore:` for Cockpit), so the desk fires it by itself and the board lists it under "Fix built, release pending" until then. Recipe in CARDS.md, "Release triggers".
- **The sweep pauses, the desk decides.** `/sentry-sweep` stops at its fix-pass pause; the desk answers its `## Decisions needed` (recorded in the report with `sweep-answer.py`) and resumes the fix pass with the picks. A SWEEP run card's `Resume` takes the session over, like `Review it now`: the desk waits until that work is done.
- **The loop stays the executor.** Code work, PR babysitting and Plain validation belong to `/plain-agent-loop`; the desk only clears what waits on a person and writes captions the loop can read. The desk dispatches executors, it never runs one itself. The one exception is a pinned FAST card: fast-tracking means the validation or the handoff runs now, in this session, and like `Review it now` it takes the session over.
- **The board reads the desk.** `desk.py` writes `~/orbit-scratch/desk/board-sync.json` (parked refs with a readable "until …", live refs) and `board.sh` groups rows by it: a parked ref sits under "Waiting on others" with its trigger, a live ref under "Waiting on you", whatever the caption regexes say. A hold lapses when the loop rewrites the caption, the same rule as the desk's own deferral voiding.
- **Never write `updated` on a loop entry.** `updated` and `lastTick` are the loop's liveness signal, which the pre-flight reads. The desk writes `status`, appends to `note` with a `desk:` marker, and nothing else. Captions of non-loop cards go to `desk.json` via `desk-close.py <id> caption "<text>"`.
- **A closed batch reopens on new members.** `desk-close.py` records the member set; a SEND or STALE batch closed today comes back as soon as a member appears that was not in that set.
- **Memory informs, never speaks.** Every customer draft starts from the orbot support memory (Tobias 2026-09-24: drafts must always be informed by it), read locally from `~/orbot/support-memory` (desk.py pulls `main` at pre-flight; the pre-flight line prints the head). The customer text never reveals it. No memory for the company is a fact the checks state, never a guess from the domain.
- **Facts go up as proposals, one PR at a time.** The desk never edits `~/orbot/support-memory` in place; `memory.py propose` queues, `memory.py pr` (the `memory:pr` RUN card) opens one orbot PR with everything queued, Tobias merges it, the deploy pulls it onto the VPS, and `memory.py sync` marks the entries merged on the next run. A second batch waits for the first merge.
- **Replies are Luna's.** `Send it` on any customer-text card means `luna-send.py`, at once, with no second question; the adapter sends as the OrBot machine user and records the turn. `reply_to_thread` only on an explicit fallback after the adapter refused.
