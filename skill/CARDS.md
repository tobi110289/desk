# Cards — sources, lanes, recipes

Since 2026-10-08 the desk mod records verbs: every `desk-close.py <id> <verb> "<note>"` in the recipes below means the `desk_close` tool with `card_id`, `verb`, `note` (plus `caption` for a loop or gap card, `trigger` and `act` for a defer). The options of a card go to the pane with `desk_card` instead of a dialog. Only `desk-close.py <id> caption "<text>"` stays a Bash call.

> Since 2026-10-09 the desk is live and has no sittings (SKILL.md). Where a recipe below says "this sitting" or "next sitting", read "now" and "a later run of `desk.py`"; "ends the sitting" means the option takes the session over and the desk waits. A cap "per sitting" is a cap per run.

The desk never waits on a dispatched run. Their output lands as cards in the next sitting (newly blocked loop entries; harvested issues wait on GitHub). A dispatched agent has no MCP servers: the loop uses its GraphQL curl path for Plain, the harvest needs only `gh`.

Score = (impact weight + who-waits weight + age weight, age capped at six days) ÷ minutes × 10. Impact: P0 8, RBP 6, RBS 5, P1 4, P2 2. Who waits: customer 3, person 2, agent 2, nobody 0. Cheap, high-value cards float; a batch scores like its most urgent member and costs the sum of its members. A card where an agent or a PR stopped for the person (SEND, REVIEW, INBOX, STUCK) ranks in its own bracket, 100 plus its score: above every card that waits on nobody and above customer cards without an event today, under today's customer events and the top list (2026-10-20: a PR that asked for a human sat at 3, under tasks at 20).

## A brief, not a draft

The pane is read by someone who has not opened the file (Tobias, 2026-10-14: "do you think someone who has been working for 8 hours can still understand wtf this is supposed to mean?").

Every card has the same shape (Tobias, 2026-10-14: "i need to clearly see, why a card is on the desk in the first place, what am i to decide and for what"). The pane shows WHY, DECIDE and THEN as labelled lines above the fact and the draft, then the options.

- `why`: one sentence. What put the card on the desk, since when, and who waits: "Dana wrote at 09:11 today and has had no answer", "this file has sat untriaged since 26 Aug, nobody waits".
- `decide`: the one question in one sentence: "Send Dana this answer as Luna?", "Hand the two Hub bugs to agents and close the third file?".
- `then`: one or two sentences. What the recommended pick sets in motion, and what is at stake if nothing happens: "Two agents start today; left alone the bugs stay live on Hub."
- `fact`: one plain sentence, under 140 characters, what the case is and what changed.
- `draft`: at most three numbered lines for a batch or task card, one short paragraph for a reply card. Each line names the thing in product words (what a user sees or cannot do), says whether it is still true, and ends with the verb.
- Never in any of the five fields: file paths, function, hook or variable names, commit hashes, entity ids and UUIDs, status enum values, ticket folder slugs, backticked code. They go into the file, the `note` on close, or the PR. PR numbers, thread refs, ticket ids, dates and amounts stay.
- A customer reply keeps its own rules (du/Sie, signed as Luna). It skips the three-line cap, not the ban.

`desk_card` needs `why`, `decide`, `then` and `fact`, and refuses a card that lacks one, naming the field. It checks all five fields against these rules and refuses a brief that breaks them, naming each word to rewrite. The rewrite of a bad card reads like this: "1. Hub bug: a resumed booking whose product never comes back stays on the loading screen forever. Still true. Hand it to an agent."

## Lanes

Every lane's `fact` and `draft` follow "A brief, not a draft" above: plain words, no code.

**A checked draft puts the send on the pane** (Tobias, 2026-10-14). REPLY, NOTIFY, PROMISE and FAST cards end in customer text. When the agent holds a checked draft for one (every claim verified live, the text on the clipboard and in `~/orbit-scratch/desk/drafts/<ref>.txt`), the card's options are `Send it · Edit then send · I sent it already · Defer · Drop`, with `Send it` first. The pick `Send it` on the pane is the send approval: the agent sends at once and asks nothing more. `Edit then send` takes the edit in one `AskUserQuestion` (free text), writes the file, then sends. Verbs: `Send it` and `Edit then send` are `delegate`, `I sent it already` is `do`. The lane's other set below holds only while there is no checked draft: open checks remain, the thread is unclaimed, or its Hermes brief is unvalidated. That is when `Draft the reply` or `Claim + validate now` lead.

## Recipes

### SEND — a worker that stopped for Tobias, or a line it proposes in its idle prompt

Members come from the screen source (`desk/screens.json`, one row per in-flight terminal). Each member carries `screen`: `staged_line_typed` (the line in `staged`; since 2026-09-24 this is Claude Code's ghost text, the worker's own proposed next prompt, never a keystroke Tobias owes: judge it like an agent suggestion, and since 2026-10-19 its wording changes do not reopen a closed batch), `picker_or_question_waiting` (`picker` = the options, `question` = what the agent asked), `sign_off_waiting` (`question`), or a `prefilled` line the desk wrote for an idle worker whose PR waits on HORST's changes or on red CI. The batch is one card, one answer per member; it outranks NOTIFY and STUCK because every member blocks a whole PR for one keystroke.

Prepare: `superset terminals read --host <host> --workspace <ws> --terminal <t> --max-lines 6` for each member (entries without `host` are local: omit the flag). The staged text is the `❯ …` line. A spinner (`✻ …`) means the agent is busy: skip the member this sitting. Preview: `T-112  "apply the plan"  (agent idle, PR #2944 CHANGES_REQUESTED)`.
Execute `Send as staged`: `superset terminals send --host <host> --workspace <ws> --terminal <t> --text "<the full staged text>"` (a bare Enter is a no-op and a space clears the box; always resend the full text, and never let the text start with `/`). A `prefilled` member sends the desk's line the same way. A `sign_off_waiting` member takes the answer Tobias gives as the text. Caption via `desk-caption.py <ref> 'sent: "<text>" <HH:MMZ>; agent working'` (stamps the rewrite; the screen source re-reads the terminal on the next run anyway). A staged line that starts with `/` (`/human-review 3253`) is a skill invocation: run it here or hand it to the worker as prose, never send it as typed.

### Sending as Luna — every customer reply the desk sends (Tobias, 2026-09-24)

**First contact footer (Tobias, 2026-10-16):** when the thread's customer or company has never had a Luna turn (no earlier "Luna reply" note on their threads, no requester file in the support memory), the draft ends with a footer under the sign-off, in the customer's language and address form: "Luna ist der KI-Assistent von Orbit. KI kann Fehler machen. Wenn etwas unklar ist, antworten Sie einfach auf diese E-Mail, dann schaut ein Mensch aus dem Orbit-Team darauf." (du / English equivalents say the same three sentences). It is part of the draft file and goes through the same checks.

Why: a reply sent as Luna (the OrBot machine user) makes the customer's answer route into the adapter's `luna_followup` Hermes job, and the customer sees one consistent machine user. Spec and status of the adapter feature: `~/orbit-scratch/luna-operator-send/PRD.md` (orbot PR `feat/operator-luna-reply`; live once `ORBOT_ENABLE_OPERATOR_LUNA_REPLY=true` and `ORBOT_OPERATOR_API_TOKEN` are set in the adapter's `.env`, config.json `sendEnvFile`).

Execute: write the approved draft to a file (`pbpaste > ~/orbit-scratch/desk/drafts/<ref>.txt`, or the file the sitting already keeps), then `python3 ~/orbit-scratch/desk/luna-send.py <ref> --file ~/orbit-scratch/desk/drafts/<ref>.txt` (`--ref` is taken from a T-ref target; pass `--ref T-…` when the target is a `th_` id). Add `--intent customer_question` when the draft asks the customer for an answer, i.e. it is the clarification a pass still needs: only then does the adapter move the thread to needs-info with the ball on the customer (orbot #801 / PR #802, Tobias 2026-10-13, option B). A thanks or a status line stays on the default intent and changes no readiness. The script queues the reply on the adapter over `ssh <sendHost>` and polls until the worker has sent and verified it (a few seconds, `--wait 90`). Exit 0: sent, the line shows the turn count (`turn 2/4`); caption `replied as Luna <HH:MMZ>; …`. Exit 4: queued, not yet sent: `luna-send.py --status <actionId>` a minute later, never a second send. Exit 5 (`failed`, `needs_human_recovery`, `max_turns_reached`): read the reason (a human already answered, the thread is closed, the Slack source is gone, four Luna turns spent); the card keeps its draft and gets a follow-up question with the reason. Exit 3 (refused before queueing: leak guard 422, flag off, auth, terminal readiness): show the reason. Before it queues, the script reads `agent_readiness`: on `ready-for-human` or `wontfix` the adapter refuses operator sends (orbot gate), so it stops with exit 3 and queues nothing. Recover by hand: set `agent_readiness` to `needs-info`, send, set it back. A failed action blocks the identical text, so change one word before the resend. `--allow-terminal-readiness` skips the check when the field is flipped and Plain lags. For any other refusal: a 422 names what the guard saw (a tenant id, an internal source): fix the text and resend, or `--force` only when Tobias reads the guard result and says so. Fallback `reply_to_thread` under Tobias's user only when the adapter is down or the feature is not deployed yet, and only on an explicit `Send it as myself` answer; caption `replied (own user, Luna path unavailable: <why>)`.

Never: a second `luna-send.py` for the same text (the adapter dedupes by thread + text, but a changed text is a new turn), a send on `Edit then send` before the edit is in the file, or a send when a customer-visible message of ours is newer than the draft.

## Triggers for `defer`

`YYYY-MM-DD` (date), `YYYY-MM-DDTHH:MMZ` (same-day time, UTC), `pr-merged:<n>` (fires when the orbit PR is merged; `pr-merged:orbot#<n>` for orbot), `a2a:<taskId>` or `a2a:<agent>:<taskId>` (fires when that A2A task I sent is completed with a human reply, or cancelled; `desk.py` reads the task on the hub and puts the reply into the card), `manual:<text>` (fires only when Tobias says so in a later sitting). Every deferral carries the act to take when it fires; `desk.py` re-surfaces the card then, and never before.
